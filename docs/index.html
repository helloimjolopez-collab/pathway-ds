2.1

Purpose & Scope

Full audit of the Pathway Design System (Figma) and the PMM Horizon live application, establishing a shared baseline for all subsequent component authoring work.

This document covers three interconnected deliverables: an honest assessment of the current state of the Pathway Design System in Figma; a full inventory of UI patterns present in the PMM Horizon application; and a prioritised, effort-estimated build list that bridges the two.

The Side Navigation component — authored and marked Ready for Dev — serves as the reference standard throughout this audit. The criteria used to consider that component complete are applied consistently to every other component in this assessment.

📌 Reference Standard

The Side Navigation component is the only component currently confirmed as fully authored. All other components are assessed against the same eight-criteria standard below — most fall significantly short. This is expected: the purpose of this audit is to define exactly where the gaps are, not to over-report completeness.

Completeness Criteria

A component is considered complete only when all eight of the following criteria are met simultaneously. These criteria apply equally — a component that scores 7 out of 8 is not complete. The ❇️ Ready for Dev marker means implementation can begin — it is a lower, pragmatic threshold, not confirmation that all eight criteria are met.

⚠ Note on the ❇️ Ready for Dev marker

The ❇️ emoji on Figma page names is the "Ready for Dev" marker in this file — it means the component has been designated as ready enough to begin implementation. It is a starting-point signal, not a quality certification. A component carrying ❇️ may still have gaps against the eight criteria above: missing states, hardcoded values, incomplete documentation, no prototype. The eight criteria define what fully authored means — ❇️ marks the threshold above which implementation work can begin in parallel with continued design refinement.

Criterion V · Variant Economy
All required states, and only those

All interaction states and variant dimensions required by the spec are present, systematically named, and organised. Equally important: no speculative, redundant, or untriggered variants exist. Every variant's presence is justified by a documented interaction requirement. Variant properties are named semantically (e.g. State=Hover, not "blue version").

Criterion N · Naming & Structure
Every layer is descriptively named

No auto-generated layer names ("Frame 633265", "Group 1073714087"). Every layer name reflects what it is conceptually. Library icons used throughout — no raw vectors, no embedded SVGs, no image assets substituting for icons. Library typography styles and variables referenced directly — no inline font family, size, weight, or letter-spacing definitions.

Criterion T · Full Tokenisation
Zero hardcoded values, anywhere

Every fill, stroke, typography property, spacing value, border radius, shadow, and opacity references a Figma variable. No hex values, rgba values, pixel measurements, or font definitions are hardcoded directly in the component. Variables reference the semantic layer (e.g. text/base/primary), not primitives directly (e.g. not color/black-gray/white). All variable references resolve — no broken links, no hardcoded fallback values masking broken token paths.

Criterion D · Comprehensive Documentation
Full spec, not just a notes box

A documentation frame exists on the component page and covers all of: component purpose + when to use / when not to use; all variant properties with visual examples; interaction states and what triggers each; responsive behaviour and breakpoints; animation and transition specs (what animates, duration, easing); keyboard navigation and focus order; ARIA roles, labels, and state attributes; colour contrast table for all colour combinations; design notes and edge cases; implementation notes for developers; known exceptions and platform-specific behaviour.

Criterion P · Interactive Prototype
A demo that shows, not describes

A linked Figma prototype exists that demonstrates all primary interaction states (hover, focus, active, disabled, error where applicable). The prototype is accessible directly from the component page — not buried in a sub-frame or separate file. It shows responsive behaviour where the component changes across breakpoints. It must be usable by a developer as a behavioural reference without needing to read the docs frame.

Criterion A · Accessibility
WCAG 2.2 AA across every variant and state

The component meets WCAG 2.2 AA as a hard requirement — not aspirationally. This means: all colour combinations in all states pass 4.5:1 contrast (text) and 3:1 (non-text UI). All interactive elements are keyboard-reachable with a visible focus indicator. All controls have correct ARIA roles, labels, and state attributes. Touch targets meet the minimum 44×44px. Motion respects prefers-reduced-motion. These must be validated per state, not just for the default variant. A colour contrast table documenting every combination must exist in the documentation frame.

Criterion M · Machine & Agent Readability
Fully consumable by agents and automated tooling

The component must be operable and understandable by an agent navigating the product on behalf of a user — for example, an AI agent running a background check in PMM, or an automated test runner interacting with the component. Requirements: all interactive elements carry unambiguous, unique accessible names (no generic "Button" or "Click here"). Semantic HTML roles are specified in the documentation frame so that implementations use the correct element. All component states are programmatically detectable (aria-expanded, aria-selected, aria-disabled etc.). The component's purpose, inputs, outputs, and behaviour are machine-readable — meaning structured, not buried in prose. Field labels are never purely visual. Error messages are associated programmatically with their input. The documentation frame must include a structured data specification section listing: element role, accessible name source, state attributes, keyboard contract, and expected DOM structure.

Criterion R · Fully Authored
All seven criteria confirmed, post-review

The component page has been reviewed against all seven criteria above and a peer design review has been completed. This is the fully-authored standard — distinct from the ❇️ designation, which means implementation can begin but does not confirm all criteria are met. Criterion R confirms the design work is genuinely complete.

Effort Scale

The following scale is used throughout the priority build list. Estimates assume a single senior designer working in Figma and include component authoring, tokenisation, documentation frame, and review cycles.

S  Small

≤ 3 days. Adjusting or filling gaps in an existing component — adding a missing state, resolving a token, updating docs.

M  Medium

3–7 days. Significant rework of an existing component, or authoring a simple new atom from scratch with full documentation.

L  Large

1–2 weeks. Complex new component with multiple variants, interaction states, and full documentation — or a simple organism.

XL  Extra Large

2–4+ weeks. A full organism (e.g. Data Table with all controls) or a screen template. Should be scoped as its own work item.

Part A — Pathway Design System Audit

Assessment of the Pathway Design System file (Figma file: 3sw45aVcngFAmpbP6cfrXP). Token pipeline readiness, token architecture issues, and component library status.

A0 · Token Pipeline Readiness

The SOW requires establishing a token pipeline — a mechanism by which Figma variables are exported and consumed reliably as CSS custom properties, design tokens (W3C DTCG format), or equivalent outputs for the Blazor component library. This section assesses whether the current Figma variable file is in a state that supports this.

🔴 Assessment: Not Pipeline-Ready

The current variable file cannot be reliably exported into a stable token pipeline. Attempting to build an extraction and consumption workflow now would produce an output that requires significant reworking once the underlying variable issues are resolved. Establishing the pipeline must be sequenced after the token architecture clean-up (Item 0 in the Priority Build List) is complete.

What "pipeline-ready" means

For variables to be reliably consumed into code, the following conditions must hold:

  • 📐
    Stable, consistent naming convention Token names follow a single predictable pattern (e.g. lowercase slash-separated paths: color/brand/primary) applied uniformly across all collections. The output CSS custom property name is derived directly from this path — inconsistent casing, mixed separators, or spaces in names produce malformed output.
  • 📐
    Single source of truth per value type One active colour collection, one typography collection, one spacing collection. Multiple active collections for the same value type mean the pipeline has to make arbitrary choices about which collection to export — creating silent inconsistencies.
  • 📐
    Clean semantic layer over primitives Components consume semantic tokens (text/base/primary, fill/surface/default) not primitive values directly (color/black-gray/white). This is what makes theming, dark mode, and brand customisation work without editing every component. The pipeline exports the semantic layer as the primary contract with code.
  • 📐
    Explicit include/exclude decisions per collection Not every Figma variable needs to go into the code output. A clear decision must be made for each collection before the pipeline is configured.
  • 📐
    No broken references or hardcoded fallbacks Variables that reference other variables must all resolve. Hardcoded fallback values in variable references (e.g. var(--text-base-primary, #363636)) mask broken token paths and prevent automated validation from catching errors.

Pipeline blockers — summary

  • 🔴
    Emoji in a variable name: ❇️ Label/Menu/Large/Medium CSS custom property names cannot contain emoji. Any token pipeline will either fail, strip the emoji silently, or produce malformed output. The ❇️ Ready for Dev marker belongs on Figma page names only — not inside variable names.
  • 🔴
    Casing split within the semantic tier fill/auxiliary/medium-contrast (lowercase) and Fill/Static/Info/Subtle (Title Case) are in the same tier. A Style Dictionary config treats casing as significant — this produces inconsistently-formed output from the same collection. One convention must be applied uniformly across all tiers.
  • 🔴
    Two active colour collections ("Color" and "Color 2 wip") Components reference variables from both collections. The Global Nav uses paths from what appears to be the old collection; Side Nav uses Title-Case semantic paths from the new one. Migration must complete and the old collection deprecated before any pipeline configuration is meaningful.
  • 🔴
    Variable search returns empty — likely a library publishing gap All variable search queries returned no results despite variables being confirmed present. Verify in Figma: Variables panel → each collection → "Publish to library" toggle. If collections are unpublished, the Figma REST API's /variables/local endpoint and all external token tools cannot access them.
  • 🔴
    Component token layer not universally applied Side Nav correctly uses component-scoped tokens throughout. Global Navigation uses hardcoded hex values and appearance-based primitive paths. Until all components reference the component token layer, the pipeline output will be inconsistent — some components will consume semantic tokens, others will bypass them entirely.
  • 🔴
    Hardcoded fallback values masking broken token references var(--text-base-primary, #363636) renders correctly even if the CSS variable is never emitted by the pipeline. Fallbacks must be removed once the pipeline is running so that missing tokens are detectable.
  • 🟡
    Typography: individual properties vs composite — requires a contract decision Each text style has five individual variable properties plus a composite Font() reference. The pipeline should expose one contract (individual or composite) per text style, not both. Decide which consumers (CSS vs Blazor) need which format, document it, then clean the export accordingly.
  • 🟡
    Component radius tokens carrying hardcoded values instead of aliasing global scale Component/NavItem/Large/Radius/Radius = 8 should be an alias of Border Radius/S = 8, not a standalone value. As-is, changing the global radius scale will not propagate to component-level radius tokens.

What the Side Nav shows is achievable

The Side Nav demonstrates the intended architecture working correctly: Surface/Nav/Light (semantic) → Fill/Contextual/NavItem/Base (component) → correct render. The accessibility token layer (Accessibility/Touch Target/Optimal/Size/Width = 48, encoding WCAG minimum touch targets) is genuinely well-considered and uncommon — it should absolutely be part of the code output. The architecture is sound. The problem is inconsistent application: the pipeline work is fix the blockers above, then extend the component token layer to every component, then configure the export.

A1 · Token Architecture

The Pathway system uses a three-tier token architecture: brand primitives → semantic fill/text/icon/stroke tokens → component-level tokens. This structure is sound and aligns with current industry standards. However, the current file contains several systemic issues that must be resolved before component authoring can proceed reliably. These are not style preferences — they are blockers.

🔴 Blocking — Token Issues Must Be Resolved First

Every component authored before the token architecture is cleaned up will need to be revisited after the migration completes. Authoring components on top of an unstable token foundation creates rework that compounds with each new component added. The token clean-up is the pre-requisite for all other work in this project.

  • ⚠️
    Mid-migration: "Color" and "Color 2 wip" collections coexist Two colour variable collections are active simultaneously in the published file. Components may be referencing either collection — creating inconsistency and making it impossible to audit tokenisation state accurately. The migration must be completed and the legacy collection deprecated before component work begins.
  • ⚠️
    Legacy token still active: Old/→ Card This deprecated token is still present in the published file. It is unclear which components — if any — still reference it. It needs to be traced and removed, or updated to the current token path.
  • ⚠️
    Test styles in the published file: Halo 1/2/3 Test Placeholder/test colour styles are visible to all consumers of the file. These should never exist in a published system file. They need to be removed immediately.
  • ⚠️
    Typography naming is appearance-based, not role-based The token Bold/M describes what the text looks like, not what it is for. A semantic system requires role-based naming such as body/strong or heading/sm. This needs to be resolved as part of the token clean-up and all component documentation updated to reference the new names.
  • ⚠️
    Capitalisation inconsistency across token names Token name casing is inconsistent across collections, which creates friction for developers consuming the system and makes token references harder to verify. A naming convention should be established and applied uniformly.
  • 🔵
    Light/Dark mode token decisions unresolved Several components — including Button — have unresolved light/dark mode token states. The component cannot be correctly tokenised until the semantic layer is clear on which colours apply in each mode. This is not just a Button issue; it will affect every component that has a colour-sensitive state.
  • 🔵
    Desktop/Mobile multi-mode variables not confirmed Variable modes for responsive contexts (desktop vs. mobile sizing, spacing) have not been confirmed in the file. Retrofitting multi-mode support after components are authored is significantly more expensive than building it in from the start. A decision on whether multi-mode is required for Phase 1 should be made before authoring begins.

C0 · Prioritisation Logic

The build sequence below follows this explicit logic. Each layer depends on the layer above it being stable.

# Layer Reason
1st Token system clean-up Nothing can be authoritatively tokenised until the Color migration is complete, legacy tokens removed, and light/dark mode decisions made. Building on unstable tokens creates rework that multiplies with every component added.
2nd Existing atoms with known gaps Button is already marked ❇️ (Ready for Dev) and partially authored. Closing its gaps is a small effort with high payoff — every screen uses buttons, and they form the baseline confidence signal for the dev team.
3rd High-frequency form atoms Text Input, Dropdown, Checkbox, Radio, Toggle appear on every single screen. These must be complete before any form-heavy screen (Invite, Settings) can be designed or built. They are also the prerequisite for the Wizard organism.
4th Data Table organism The dominant pattern across three primary screens. Authoring this organism is the single highest-impact deliverable — it unlocks Background Checks, Screening Flows, and Child Safety in one shot. It is also the most complex item and should be treated as a standalone work stream.
5th Navigation & utility atoms Badge, Tabs, Breadcrumb, Tooltip, Modal, Avatar are needed for Applicant Profile and supporting views. Lower urgency than table atoms because fewer screens depend on them, but they unlock detail views.
6th Remaining organisms Wizard, Settings Form Section, Screening Flow Card can only be correctly authored once their constituent atoms are stable. Sequencing them after the atoms avoids rework loops.
7th Screen templates Templates are assembled from finished organisms. They are fast to produce once atoms and organisms are done — attempting them earlier would require placeholder components and create technical debt.
